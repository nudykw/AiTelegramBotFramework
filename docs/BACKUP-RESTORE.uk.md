# Інструкція з аварійного відновлення та ручного повернення до робочої версії

Цей посібник описує роботу автоматичної системи створення резервних копій та відкату (rollback), вказує місця збереження бэкапів і надає покрокові інструкції для ручного відновлення середовища продакшену оператором у разі критичного збою.

---

## 1. Огляд автоматичної системи

Під час кожного розгортання проекту (через `.forgejo/workflows/deploy.yml`) на прод-сервері виконується такий ланцюжок дій:
1. **Попередня перевірка місця (Pre-flight Disk Check)**: Перевіряє наявність щонайменше 2 ГБ вільного місця в розділі `/home/nudyk`. Якщо місця недостатньо, розгортання зупиняється *до* вимкнення чи зміни будь-яких служб.
2. **Ротація резервних копій**: Автоматично зберігає лише **3 найновіші бэкапи** у директорії `/home/nudyk/deploy_backups/`, щоб запобігти переповненню диска.
3. **Холодний бэкап (Cold Backup)**:
   - Повністю зупиняє поточні служби (`docker compose down`).
   - Копіює файли конфігурації `.env` та `Configs/appsettings.json` у папку резервної копії.
   - Архівує критично важливі Docker-томи (`postgres_data`, `qdrant_data`, `cloudbeaver_workspace`) у стиснутий архів `volumes.tar.gz`.
4. **Розгортання та перевірка здоров'я (Healthcheck)**:
   - Стягує останній код гілки `prod`, об'єднує секрети, створює файл `git_info.json`, збирає нові Docker-образи та запускає контейнери.
   - Очікує протягом 60 секунд, доки контейнер бота успішно перейде в статус `healthy`.
5. **Автоматичний відкат (Rollback)**: Якщо будь-який крок (збірка, міграція або перевірка запуску бота) завершується помилкою, система перехоплює збій і автоматично повертає прод до точного стану, який був до початку деплою.

---

## 2. Структура файлів резервної копії

Усі резервні копії зберігаються на прод-сервері за шляхом:
```bash
/home/nudyk/deploy_backups/backup_РРРРММДД_ГГХХСС/
```

Всередині кожної папки бэкапу містяться:
*   `volumes.tar.gz` — архів, що містить точні копії даних усіх критичних Docker volumes.
*   `.env.bak` — резервна копія конфігураційного файлу оточення.
*   `appsettings.json.bak` — резервна копія основного конфігураційного файлу налаштувань додатку.

## 3. Ручне відновлення системи

Якщо деплой зазнав невдачі, автоматичний rollback *повинен* самостійно відновити роботу системи. Однак, якщо процес автоматичного відкату перервався або завершився помилкою через глибокі проблеми на рівні сервера, оператор може виконати ручне відновлення за інструкцією нижче.

### Крок 1: Підключіться до сервера
Підключіться до прод-сервера через SSH за вашими доступами розгортання:
```bash
ssh nudyk@<ваш-хост-деплою>
```

### Крок 2: Перейдіть у директорію проекту
Перейдіть до кореневої папки проекту:
```bash
cd /home/nudyk/Sites/GptChatTelegramBot
```

### Крок 3: Виберіть потрібну резервну копію
Перегляньте список доступних папок бэкапу та знайдіть останню стабільну версію:
```bash
ls -la /home/nudyk/deploy_backups/
```
Для прикладу припустимо, що остання робоча копія лежить у `/home/nudyk/deploy_backups/backup_20260530_093000`.

### Крок 4: Зупиніть усі служби
Переконайтеся, що всі запущені контейнери (включаючи ті, що працюють некоректно) повністю зупинені:
```bash
docker compose --profile postgres --profile cloudbeaver --profile aspire down
```

### Крок 5: Відновіть конфігураційні файли
Скопіюйте стабільні конфігурації з бэкапу назад у проект:
```bash
cp /home/nudyk/deploy_backups/backup_20260530_093000/.env.bak .env
cp /home/nudyk/deploy_backups/backup_20260530_093000/appsettings.json.bak Configs/appsettings.json
```

### Крок 6: Відновіть Docker Volumes
Відновіть бази даних та налаштування з архіву `volumes.tar.gz`. Ми запускаємо тимчасовий контейнер Alpine, який монтує томи та розпаковує архів безпосередньо у них:
```bash
docker run --rm \
  -v postgres_data:/volumes/postgres_data \
  -v qdrant_data:/volumes/qdrant_data \
  -v cloudbeaver_workspace:/volumes/cloudbeaver_workspace \
  -v /home/nudyk/deploy_backups/backup_20260530_093000:/backup \
  alpine sh -c "rm -rf /volumes/* && tar -xzf /backup/volumes.tar.gz -C /volumes"
```

### Крок 7: Відкотіть кодову базу в Git
Якщо помилка була спричинена багом у коді, визначте останній робочий хеш комміту (його можна подивитися через `git log` або дізнатися з назви папки бэкапу) та виконайте hard-reset:
```bash
# Переглядаємо останні комміти
git log --oneline -n 10

# Робимо жорстке повернення коду на стабільний комміт (наприклад, a1b2c3d4)
git checkout <stable-commit-hash>
git reset --hard <stable-commit-hash>
```

### Крок 8: Запустіть контейнери
Зберіть образи заново (після відкату коду) та запустіть контейнери у фоновому режимі:
```bash
docker compose --profile postgres --profile cloudbeaver --profile aspire up -d --build
```

### Крок 9: Перевірте статус системи
Переконайтеся, що всі служби успішно піднялися та функціонують без помилок:
```bash
# Перегляд статусів контейнерів
docker compose --profile postgres --profile cloudbeaver --profile aspire ps

# Перегляд логів бота
docker compose logs -f bot
```
Як тільки бот та бази даних повідомлять про здоровий статус, відновлення системи можна вважати успішно завершеним.
